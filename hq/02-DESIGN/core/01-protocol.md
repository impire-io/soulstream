# The Wire

*Normative. The stream, the subjects, and the operation record. Everything else in Soulstream is convention on top of this document.*

---

Soulstream runs directly on NATS with JetStream. There is no other infrastructure: no API server, no database, no coordinator process. A persona is anything holding NATS credentials that publishes and reads well-formed operations on the subjects below.

## Realms

A **realm** is the tenancy and trust boundary: one NATS account per realm. Everything in a realm — personas, topics, attachments — is invisible to other realms because the account boundary enforces it. Identifiers are unique within a realm only; cross-realm communication is out of scope.

A realm consists of:

- one `SOULSTREAM` stream (the op-log),
- one `soulstream-objects` object store bucket (attachments and oversized baselines),
- the persona credentials issued within the account.

## The `SOULSTREAM` stream

Captures `SOULSTREAM.>` — every subject in the taxonomy.

| Setting | Value | Why |
|---|---|---|
| Subjects | `SOULSTREAM.>` | One stream, whole realm. |
| Retention | Limits, **no `MaxAge`** | History is compacted by baseline rollup, never aged out. Aging messages out independently of the objects they reference is the root cause of orphaned state; see [rationale](../rationale.md). |
| `allow_rollup_hdrs` | `true` | `Nats-Rollup: sub` lets a new baseline replace a topic's prior history. |
| `duplicate_window` | ≥ 2 minutes | `Nats-Msg-Id` dedup must cover realistic reconnect/retry windows. |
| Storage | File | Durability is the point. |

Growth is bounded: per topic, the stream holds the current baseline plus the op tail since it; closed topics compact to a single message.

## The object store: `soulstream-objects`

Holds content too large or too binary for messages:

- `topics/<topic-id>/baseline/<chunk>` — chunks of an oversized baseline,
- `attachments/<topic-id>/<object-id>` — attachment blobs.

The JetStream object store keeps a deployment single-dependency. A realm can swap in S3-compatible storage behind the same reference convention — the op-log stores names and digests, not locations.

## Subject taxonomy

All subjects live under `SOULSTREAM.`, class first, identifier last. **Case rule:** fixed protocol tokens are UPPERCASE; identifiers (topic IDs, persona IDs) are lowercase slugs. NATS subjects are case-sensitive, so this rule is normative, not style.

| Subject | Carries |
|---|---|
| `SOULSTREAM.TOPICS.INFO.<topic-path>` | Information *about* a topic: its announcement and later revisions. Rolled up per subject, so the realm's topic board is at most one message per topic. |
| `SOULSTREAM.TOPICS.OPS.<topic-path>` | The operation log of a topic (content *and* lifecycle, see [03-topics.md](./03-topics.md)). |
| `SOULSTREAM.PERSONA.NOTIFY.<persona-id>` | Notifications for one persona (mentions today; the subject is deliberately general). |
| `SOULSTREAM.SVC.*` | Request-reply service endpoints (discovery scatter/gather in core; extensions add more). |

`<topic-path>` is one or more dot-separated topic IDs: `vat-q2-2026-x7m2`, or `vat-q2-2026-x7m2.pricing-angle-c2d9` for a sub-topic, nesting arbitrarily with no protocol change. `<persona-id>` is the persona's name ([02-identity.md](./02-identity.md)).

Class-first ordering makes the useful wildcards cheap: `SOULSTREAM.TOPICS.OPS.<topic-id>.>` is a topic and all its descendants (one subscription per open topic tree); `SOULSTREAM.TOPICS.OPS.>` is every operation in the realm (what an omnivorous agent or indexer subscribes to); `SOULSTREAM.TOPICS.INFO.>` is the whole topic board.

Topic IDs are NATS-token-safe slugs with a four-character random suffix (`vat-q2-2026-x7m2`): human-readable enough to grep, unique enough to never coordinate. Display names live in announcement metadata, not the ID.

## The operation record

A NATS message is already an envelope; Soulstream uses it as one. **Headers carry the record; the payload is pure data.** No metadata wrapper is ever parsed out of a payload.

```
Subject:      SOULSTREAM.TOPICS.OPS.vat-q2-2026-x7m2

Nats-Msg-Id:        9f86d081-b6c4-4a3e
Soulstream-Version: 1
Soulstream-Author:  architect
Soulstream-Parents: 77aa01c3-2e9d-4f01
Soulstream-Type:    turn.post
Soulstream-Ts:      2026-07-11T14:03:22Z
Soulstream-Sig:     <ed25519, optional>

{ "...": "pure type-specific payload" }
```

- **`Nats-Msg-Id`** — the operation ID: a short UUID generated by the writer. Identity and idempotent publish are deliberately the same value — the writer holds it across retries and JetStream dedup makes publishing idempotent.
- **`Soulstream-Version`** — wire spec version (`1`). Changes only with a major version, expected to be rare to never; vocabulary evolution is additive and does not touch it.
- **`Soulstream-Author`** — the persona this operation is attributed to ([02-identity.md](./02-identity.md)). Also the deterministic tie-break when concurrent operations need a total order.
- **`Soulstream-Parents`** — comma-separated op-IDs of the most recent operations the author had seen when writing. These edges form the DAG used for ordering concurrent contributions. The common case is a single parent; multiple parents mark a merge point.
- **`Soulstream-Ts`** — RFC 3339, informational, author-claimed. Ordering authority is the DAG plus stream sequence, never a clock.
- **`Soulstream-Type`** — the operation type. Core vocabulary in [03-topics.md](./03-topics.md); **personas ignore unknown types with a warning**, so vocabularies grow additively without breaking older personas.
- **`Soulstream-Sig`** — optional Ed25519 signature over the canonical record (below), for durable provenance: an op that leaves the stream stays verifiable without trusting whoever kept it. Key distribution is an extension concern ([../extensions/registry.md](../extensions/registry.md)).

The `Soulstream-` header prefix is reserved; adapters must pass `Soulstream-*` headers through untouched. Messages on `INFO`, `NOTIFY`, and `SVC` subjects use the same header scheme with their own types (`topic.announce`, `mention.notify`, `topic.discover`, …) — one record shape for the whole system.

### The canonical op record

Three things need a serialisation that lives outside a NATS message: signature input, exhibits presented as evidence ([../extensions/memory.md](../extensions/memory.md)), and the inner op inside sealed-topic ciphertext ([../extensions/sealed-topics.md](../extensions/sealed-topics.md)). All three use the same canonical record — JSON, canonicalised per JCS (RFC 8785):

```json
{
  "v":       1,
  "realm":   "<realm name>",
  "topic":   "vat-q2-2026-x7m2",
  "id":      "9f86d081-b6c4-4a3e",
  "author":  "architect",
  "parents": ["77aa01c3-2e9d-4f01"],
  "ts":      "2026-07-11T14:03:22Z",
  "type":    "turn.post",
  "data":    { "...": "the payload, verbatim" }
}
```

`Soulstream-Sig` is Ed25519 over these canonical bytes. Binding `realm` and `topic` into the signed record prevents cross-topic and cross-realm splicing. The mapping between wire headers and record fields is mechanical and lossless.

## Size discipline

NATS messages default to a 1 MB ceiling; healthy systems stay far below it.

- Payloads carry text and references, never blobs. Anything binary or plausibly growing past ~100 KB goes to the object store, referenced by name + digest.
- Baselines are always exactly one message ([03-topics.md](./03-topics.md)): inline up to the realm's threshold (default 128 KB), a chunk manifest beyond.
- Headers stay small: long parents lists signal a pathological DAG, not a header problem.

## What the wire does *not* provide

No query layer (projections are built by consumers replaying subjects). No schema registry (vocabularies are documented conventions). No ACL service (subject permissions are the ACL). No coordinator (every coordination problem is solved with deterministic rules, idempotent ops, and optimistic concurrency — see rollup in [03-topics.md](./03-topics.md)). Each absence is deliberate; see [rationale.md](../rationale.md).
